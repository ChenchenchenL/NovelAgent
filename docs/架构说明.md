# 个人小说创作 Agent 架构说明 v14.0

> 本文定义单作者、单机优先的长篇小说创作 Agent。
> 核心目标是让作者持续写作、局部修改并保持人物、剧情和叙事连续，而不是建设企业级多租户平台。

## 一、目标与边界

### 1.1 核心目标

- 同时支持作者手写、AI 辅写、局部续写、改写和整场景生成。
- 以场景和段落为日常生成、缓存、检查和采纳粒度，以章节为组织和发布聚合。
- 保存作者确认的正文、人物、关系、事件、时间线、剧情线和伏笔。
- 在长篇写作中发现真正受影响的内容，避免全书无差别告警。
- 区分现实事实、角色认知、谎言、传言、梦境、回忆、假设和文学隐喻。
- 控制上下文断裂、人物偏离、无效重复、节奏拖沓和 AI 水字数。
- 所有模型判断都可解释、可忽略、可纠正；作者始终拥有最终决定权。

### 1.2 非目标

多租户、组织权限、计费系统、跨区域灾备和企业审计不属于当前架构主线。个人模式仍保留项目 ID、版本和本地备份，以隔离不同小说并支持恢复。

## 二、设计原则

### 2.1 正文优先，结构化知识辅助

作者确认的正文是文学表达的第一来源。结构化事实、KG、摘要和向量索引用于检索与检查，但不能覆盖正文，也不能在抽取失败时阻止作者保存作品。

### 2.2 正典、工作区和派生数据分离

- **正典**：作者确认的正文版本和明确确认的结构化事实。
- **工作区**：手写内容、AI 流式输出、局部补丁、待确认抽取和检查报告。
- **派生数据**：全文索引、向量、KG 投影、层级摘要、社区摘要和质量统计。

工作区内容不会自动进入正典。派生数据可以删除并从正典重建。

### 2.3 写作粒度与发布粒度分离

- `Beat` 是规划和生成控制单元。
- `ParagraphRange` 是局部编辑与采纳单元。
- `Scene` 是连续性、上下文和增量提交的主要单元。
- `Chapter` 是多个场景的组织、整体审核和发布单元。

系统不要求作者等待 AI 生成整章，也不要求整章一次性采纳。

### 2.4 确定性规则只消费已确认结构

规则引擎可以确定性比较两个已确认的时间、人物状态或唯一物品持有关系；它不能把 LLM 对隐喻的低置信抽取当成确定事实。抽取不确定时进入人机仲裁，不进入硬拦截。

### 2.5 单机优先，增强能力按需启用

SQLite、全文索引和轻量向量检索足以支撑第一阶段。图数据库、社区聚类和 GraphRAG 是可选的离线增强能力，不进入每次写作的关键路径。

### 3.2 运行形态

第一版采用模块化单体：一个应用进程、一个 SQLite 数据库、一个本地任务表和可选的模型服务。逻辑模块保持边界，但不拆成微服务。

- SQLite 使用事务和 WAL 保存正典、工作区快照和任务状态。
- FTS5 提供专名、原句和关键词检索。
- 向量索引作为可选插件，只保存带版本的文本切片引用。
- KG 先使用节点表、边表和递归查询，必要时在内存中构图。
- 后台任务使用数据库任务表增量执行，不要求消息队列。
- 云模型优先，但外发范围默认限定为当前已打开的项目；上下文装配仍按 Token 预算选择目标章节、卷摘要或项目摘要，历史目录必须先导入并经作者确认。

### 3.3 模型分级路由

模型调用按任务风险和复杂度分级，而不是所有步骤都使用前沿模型：

| 层级 | 典型任务 | 失败或超时策略 |
| --- | --- | --- |
| `T0` 规则/本地代码 | 版本比较、时间计算、物品守恒、文本 Diff、重复指纹 | 必须本地完成，结果可复现 |
| `T1` 小模型/本地模型 | 实体识别、模态初筛、来源切片、候选摘要、套话扫描 | 降级为待确认，不阻断正文 |
| `T2` 中型模型 | Beat 计划、章节过渡建议、关系解释、初步连续性报告 | 可重试或改用 T1，保留不确定性 |
| `T3` 大模型 | 创作、复杂改写、跨卷剧情分析、最终语义复核 | 受预算和用户确认控制，失败不影响已保存正文 |

每次调用记录任务、模型、提示模板、ContextManifest、输入输出计量和结果版本。路由器根据任务类型、剩余预算、隐私策略和本地模型可用性选择层级；不能因为 T3 不可用就伪造 T3 质量。

### 3.4 跨介质崩溃恢复

正文文件、SQLite 和向量索引不共享一个事务，因此采用可校验的提交日志和重建策略：

1. 先在 SQLite 事务中写入正文版本、内容哈希、工作区快照和 `PendingProjection`。
2. 提交后再将正文文件按版本写入临时文件，`fsync` 后原子替换，并记录文件哈希。
3. 向量、FTS、KG 和摘要只作为可重建投影，写入带版本的任务队列。
4. 启动时执行 `novelagent fsck`：校验 SQLite 记录、正文文件哈希、快照引用、投影版本和未完成任务。
5. 发现正文文件缺失时从 SQLite 恢复；发现 SQLite 记录完整但投影缺失时重建投影；发现两者哈希冲突时保留两份并要求作者选择，绝不静默覆盖。

断电恢复以“最后一个完整正典提交”为边界。流式生成和工作区可以回退到最近快照，但不会把半段模型输出当成正典。

## 四、篇章、场景与工作区

### 4.1 内容层级

```text
NovelProject
  -> Volume（可选）
    -> Chapter
      -> Scene
        -> Beat
          -> ParagraphRange
```

阅读顺序、场景顺序和故事世界时间分别保存。倒叙或插叙不会因为章节序号靠后而被误判为发生时间更晚。

### 4.2 Beat、Scene 和 Chapter 的职责

`BeatContract` 定义一个最小叙事动作：目的、参与人物、冲突、必须产生的新信息或状态变化、目标篇幅和停止条件。Beat 通常是计划，不必作为正文正典。

`Scene` 是主要创作单元，包含 POV、地点、叙事时间、进入状态、场景目标、Beat 列表、退出状态和多个正文版本。

`Chapter` 聚合有序场景，保存章节契约、当前工作版本和已发布版本。章节发布前允许部分场景已经确认、部分场景仍在工作区。

### 4.3 持久化工作区

`GenerationWorkspace` 保存：

- 当前基础场景/正文版本。
- 作者未提交手写内容和定时自动保存快照。
- AI 已生成并审核的流式片段。
- 选区、局部补丁、撤销链和候选方案。
- 本次 `ContextManifest`、模型和提示模板版本。
- 待确认的逆向抽取主张、检查结果和作者决议。

浏览器断开、模型失败或应用重启后可以从最近快照恢复。工作区保存不是正典提交，不触发下游影响传播。

### 4.4 增量生成与局部采纳

作者可以针对 Beat、场景、若干段落或光标位置请求续写。AI 返回 `TextPatch`，标明基础版本、插入或替换范围以及生成来源。

局部采纳时：

1. 验证目标范围仍基于同一正文版本。
2. 只把选中的补丁合并到新的 `SceneRevision`。
3. 对发生变化的文本范围执行逆向抽取和局部检查。
4. 保存接受与未接受片段的来源，不丢失候选方案。
5. 更新场景的暂定退出状态；章节发布时再生成正式 `ChapterOutput`。

多个局部提交可以组成一个章节，不要求整章重新生成。

### 4.5 状态机

场景状态：

```text
PLANNED -> WRITING -> PARTIALLY_ACCEPTED -> SCENE_ACCEPTED
                    \-> EXTRACTION_PENDING
```

章节状态：

```text
IDEA -> OUTLINED -> IN_PROGRESS -> READY_FOR_REVIEW -> RELEASED
                            \-> LOCALLY_STALE
```

`LOCALLY_STALE` 只表示某些依赖需要复核，并携带具体受影响场景和原因，不等于整章失效。

## 五、手写、AI 辅写与逆向抽取

### 5.1 三种同等地位的工作流

1. **作者手写**：作者直接编辑，系统保存工作区并对改动范围做逆向抽取。
2. **AI 辅写**：AI 对选区续写、改写、压缩或提供候选，作者局部采纳。
3. **计划生成**：作者先确认章节/场景/Beat 契约，再让 AI 逐 Beat 或逐场景生成。

架构不把“AI 生成整章”设为默认路径。

### 5.2 正典逆向抽取

手写或外部导入正文的处理流程：

```text
文本 Diff
  -> 识别人名、地点、物品和事件候选
  -> 输出带模态和来源范围的 ClaimCandidate
  -> 实体消歧与置信分级
  -> 展示新增、修改、冲突和不确定项
  -> 作者批量确认、逐项修正或稍后处理
  -> 写入结构化正典并建立来源和依赖
```

正文可以先被作者确认，而抽取结果保持 `EXTRACTION_PENDING`。此时后续生成优先携带相关原文片段，并提示结构化检查能力暂时降低；系统不能因为抽取模型不确定而拒绝作者正文。

### 5.3 存量作品导入与冷启动

导入已有小说、几十万字正文、大纲或设定集时，系统不假设作者从第一章开始重新录入：

```text
文件发现与编码检测
  -> 文档分卷/分章/段落切分
  -> 原文版本化保存（先保证可回放）
  -> T1 批量识别人物、地点、物品、事件和时间候选
  -> T1/T2 生成章节/场景摘要与剧情线候选
  -> 实体别名归并、模态标注和来源绑定
  -> 作者确认核心人物、主线、关键道具和时间基准
  -> 增量建立 FTS、向量、KG 和 H-RAG 索引
```

导入任务可以暂停、重试和从任意批次继续。每批有独立检查点和成本上限；单批失败不回滚已经保存的原文。

冷启动采用三档精度：

- **快速可写**：只切章、建全文索引和提取核心实体，马上允许继续写作。
- **结构化导入**：补充人物状态、剧情线、物品和时间轴，并请求作者确认高影响主张。
- **深度回顾**：对隐晦伏笔、文风指纹和跨卷关系执行 T2/T3 分析，后台运行。

其他设定文档（人物卡、世界观、时间表）作为带来源的 `ReferenceDocument` 导入，默认是辅助资料；作者确认后才升级为 `CanonClaim`。

## 六、事实模态与置信仲裁

### 6.1 Claim 模型

所有抽取结果先成为 `ClaimCandidate`，至少包含：主体、谓词、客体、叙事时间、来源范围、模态、认知主体、抽取置信度和实体链接置信度。

### 6.2 事实模态

| 模态 | 含义 | 是否直接参与物理正典硬检查 |
| --- | --- | --- |
| `ACTUAL` | 叙事世界中已经确认发生 | 是 |
| `BELIEVED` | 某角色相信，但未必真实 | 否 |
| `REPORTED` | 传言、转述或谎言 | 否 |
| `REMEMBERED` | 回忆内容，可能不可靠 | 需作者确认 |
| `DREAMED` | 梦境、幻觉或愿景 | 否 |
| `HYPOTHETICAL` | 计划、猜测或条件句 | 否 |
| `COUNTERFACTUAL` | 明确未发生的反事实 | 否 |
| `METAPHORICAL` | 隐喻、夸张或无法按字面解释 | 否 |
| `AMBIGUOUS` | 暂时无法判断 | 否 |

同一句话可以同时产生“角色说了某句话”这一 `ACTUAL` 事件和“话中内容”为 `REPORTED` 的主张。梦境后来成为预言，必须由作者建立新的关联，不能自动把梦境升级为现实。

### 6.3 置信缓冲和人机仲裁

检查结果分为：

- `BLOCKING_CONFIRMED`：参与比较的实体、模态和两侧事实均由作者确认，且确定性规则直接矛盾。仍允许作者通过显式“修改旧正典”解决，而不是永久禁止写作。
- `REVIEW_REQUIRED`：抽取高置信但尚未确认，或存在实体消歧问题。
- `ADVISORY`：语义模型认为可能偏离、重复或不自然。
- `UNKNOWN`：证据不足，不做结论。

LLM 抽取本身永远不能直接产生 `BLOCKING_CONFIRMED`。作者手写内容可以保存；只有结构化正典如何更新需要仲裁。

## 七、人物、关系与有限知情追踪

### 7.1 人物档案和阶段状态

`Character` 保存身份、别名、背景和较稳定的核心特征。`CharacterState` 保存绑定叙事时间或场景的地点、身体状态、目标、阵营、情绪和人物弧阶段。

人物成长会创建新阶段，后续偏离检查以新阶段为基准，不把合理成长误判为违背初始人物卡。

### 7.2 关系事件和关系状态

关系不建模为一条永久的“朋友/敌人”标签：

- `RelationshipEvent` 记录结盟、背叛、援助、争执、表白等变化及来源。
- `RelationshipState` 是指定叙事时刻的推导状态，可以非对称，例如 A 信任 B、B 利用 A。

关系事件是正典；图中的人物关系边是可重建投影。

### 7.3 稀疏 Theory of Mind

系统不跟踪所有角色对所有事实的认知。只有被标记为 `NarrativeSecret` 或 `InformationGap` 的核心信息进入知情账本，例如真实身份、凶手、背叛计划和关键误会。

知情检查限定为：

- 当前场景出场人物和 POV 人物。
- 与当前 Beat 直接相关的核心秘密。
- 明确配置为需要追踪的次要角色。

未追踪不等于“不知道”，而是 `UNTRACKED`。这样避免角色数乘事实数的状态爆炸。

### 7.4 人物偏离

偏离检查覆盖稳定身份冲突、知识越界、目标/价值观异常变化、口吻漂移和关系反应异常。前两类在证据已确认时进入高优先级仲裁；性格和文风偏离始终作为带证据的建议。

### 7.5 关键物品与所有权守恒

关键物品不是人物的普通标签，而是独立的 `ItemEntity`。每件物品有固定 ID、类别、唯一性、状态、当前位置、当前持有人和来源。

物品状态通过不可变 `ItemEvent` 推进：

```text
CREATED -> HELD -> TRANSFERRED -> HIDDEN/LOST -> FOUND -> DESTROYED
```

事件必须记录发生场景、叙事时间、前状态、后状态、来源和确认状态。唯一物品同一叙事时刻只能有一个有效持有人；转移、偷窃、交换、复制和摧毁都必须是显式事件。超自然复制或分裂需要新建子物品并记录 `DERIVED_FROM`，不能让原物品凭空仍在原主人手中。

生成检查先读取目标场景的物品快照，再验证动作是否满足守恒：角色使用、赠予、遗失或携带物品必须与最近已确认状态相容。抽取不确定时报告 `REVIEW_REQUIRED`，不会把文学上的“仿佛握着旧剑”直接视为物理持有。

### 7.6 影子实体、马甲和掉马

为了支持卧底、化名、易容和“掉马”，系统区分：

- `CanonicalCharacter`：最终确认的真实人物。
- `ShadowEntity`：作者尚未确认其真实身份的叙事身份，如“黑衣人”“甲先生”。
- `IdentityHypothesis`：某个影子实体可能对应哪个真实人物、依据哪些线索、在何时可以被读者或角色知道。

影子实体拥有自己的出场、关系、知情和来源，不能在揭晓前把真实人物的全部状态泄漏给 POV。作者确认掉马时创建 `IdentityRevealEvent`，记录揭晓场景、证据、读者可见范围和角色知情变化，然后把影子实体的历史事件通过 `ALIAS_OF` 关联到真实人物；原始影子 ID 和历史来源仍保留用于回溯。

合并不是简单改 ID：

1. 校验两个实体在同一叙事时间的状态是否冲突。
2. 将可证明属于同一人的关系、物品和剧情事件建立关联。
3. 保留无法确定的早期事件为影子视图，不能追溯性地让所有人物都知道真相。
4. 重新计算掉马后受影响的场景、知情账本和伏笔，不把全书标为失效。

## 八、剧情衔接与章节过渡

### 8.1 剧情线和伏笔

`PlotThread` 跟踪主线、支线、人物弧和悬念。`PlotEvent` 记录引入、推进、转折、延迟、解决或废弃。伏笔使用 `SETUP -> DEVELOP -> PAYOFF/ABANDONED`，每次变化绑定场景和来源。

### 8.1.1 伏笔调度而非全量加载

每条伏笔额外保存目标章节区间、最早可触发章节、最晚建议回收章节、触发条件和允许的误导次数：

- `TARGET_WINDOW`：作者预期的出现或回收范围，可以是章节区间、剧情阶段或未知。
- `TRIGGER_CONDITION`：人物到达地点、获得物品、听到关键词、某事件发生或某关系达到阶段。
- `VISIBILITY`：读者可见、某人物可见、仅作者/Agent 可见。
- `PRIORITY`：主线、重要支线、背景细节。

生成某场景时，调度器先按当前章节、活跃剧情线、POV 和触发条件筛选候选伏笔，再从候选中读取摘要和原文证据。未到窗口的伏笔只保留轻量索引，不进入 Prompt；达到窗口但未满足条件的伏笔生成提醒，而不是强行揭示。

隐晦伏笔不能只依赖向量相似度。创建或确认伏笔时同时生成显式锚点：关联人物/物品/地点、可能的事件类型、目标窗口和作者关键词。揭秘章节根据锚点和 `Impact Graph` 反查所有候选 setup，再用语义模型判断是否真正 payoff。这样可以避免 Token 全量膨胀，也减少隐喻伏笔被向量召回遗漏。

### 8.2 Scene 进入与退出状态

每个确认场景生成 `SceneExitState`：

- 最后可见动作和未完成动作。
- 在场人物、位置、伤势、持有物和情绪张力。
- 新获得或暴露的核心信息。
- 已推进的剧情线、仍打开的问题和立即后果。
- 下一场景需要承接或允许跳过的内容。

下一场景使用 `SceneEntryContract` 声明继承哪些状态、发生多少时间跳跃、是否换地点/POV，以及场景目标。衔接发生在相邻场景之间，章节 `ChapterOutput` 只是该章场景输出的汇总。

### 8.3 过渡检查

过渡检查分别比较：

- 时间：连续、跳时或倒叙是否明确。
- 空间：移动是否可能，是否需要交代。
- 人物：入场、退场、伤势和持有物是否连续。
- 行动：上一场景悬置动作是否被承接或有意切断。
- 情绪：情绪突变是否有触发事件。
- 信息：角色是否突然知道未获知的核心秘密。
- POV：视角切换是否符合章节策略。

作者可以将跳切标记为 `INTENTIONAL_CUT`，系统只检查读者能否定位，不强制插入解释性过渡段。好的文学留白不能被自动“补全”。

### 8.4 时间模型

每个事件区分阅读位置、叙事时间和系统确认时间。传记回忆中的事件还记录叙述者和可靠性。未知时间保存范围或相对顺序，不伪造精确日期。

### 8.5 空间移动与耗时校验

地点由 `LocationEntity` 表示，除名称外还可保存层级、坐标或相对位置、出入口、交通方式和设定中的移动规则。项目维护 `TravelProfile` 和地点间的耗时矩阵；没有现实地理数据时，作者可以使用“步行/骑马/船/传送”等自定义距离单位。

场景退出和进入状态都记录地点与时间区间。检查器根据人物、物品或事件的连续位置，计算两场景之间的最短可能耗时，并与叙事时间差比较：

- 时间差小于最短耗时：报告空间时间硬冲突。
- 时间差不足但存在传送、飞行或特殊能力：要求引用已确认的规则或作者显式标记。
- 路线和耗时未知：报告 `UNKNOWN`，不伪造精确旅行时间。
- 有意跳切：仍需说明抵达地点和时间，但不要求描写完整旅程。

移动事件、传送事件和地点变更进入 `Impact Graph`，因此修改地图规则只影响实际使用该路线的场景。

## 九、KG、H-RAG 与 GraphRAG

### 9.1 KG 的定位

需要 KG 能力，但不需要一开始部署图数据库。正典关系和事件保存在结构化表中，KG 是用于多跳查询的投影视图，适合回答：

- 两个人物通过哪些事件形成当前关系。
- 某物品经过哪些人物和地点流转。
- 某秘密由谁知道、传播给谁。
- 某伏笔与哪些事件和人物相连。

图边必须带叙事时间、模态、来源、确认状态和版本。默认查询只返回 `ACTUAL + AUTHOR_CONFIRMED`，除非调用方明确要求角色认知或传言视图。

### 9.2 H-RAG

本文的 H-RAG 指 Hierarchical RAG。它是日常写作的主检索路径：

```text
项目/卷摘要
  -> 剧情线或人物摘要
    -> ChapterOutput / SceneExitState
      -> 场景与 Beat 摘要
        -> 原文 SourceSpan
```

续写先读取相邻场景和直接状态，再按需要向上或向下扩展。每层摘要保留来源 ID、版本和模态，最终硬事实必须能回到原文或作者声明。

### 9.3 GraphRAG 和社区摘要

GraphRAG 只用于跨卷、多跳和全局主题问题。社区摘要是派生缓存，不是正典。个人单机版采用三级策略：

1. **默认关闭自动社区聚类**：先按卷、剧情线、阵营和作者标签形成逻辑社区。
2. **后台按需生成摘要**：只为活跃剧情线或作者发起的全局问题生成，并设置 Token/时间预算。
3. **达到规模后可选聚类**：图规模和跨卷查询频率确实增加时，离线执行社区检测并缓存结果；失败不影响写作。

社区摘要失效由影响图精确定位。修改某一关系时只重建包含该边的社区和上层摘要，不扫描全部社区。

### 9.4 检索路由

| 请求 | 默认检索 |
| --- | --- |
| 继续当前段落或 Beat | 最近原文 + SceneEntry/Exit + 当前人物状态 |
| 生成下一场景 | 相邻场景 + 活跃剧情线 + H-RAG |
| 查询人物关系路径 | KG 限深邻居/路径查询 + 来源片段 |
| 跨卷伏笔或阵营分析 | GraphRAG/社区摘要 + 来源回溯 |
| 模仿已确认文风 | 向量召回相似场景，作为软参考 |
| 查专名和原句 | FTS |

GraphRAG 不进入普通段落续写的默认路径，避免高 Token、长延迟和无关全局上下文。

## 十、上下文装配与连贯性

### 10.1 ContextPack

上下文按以下优先级装配：

1. 作者当前指令、选区和 Beat/Scene 契约。
2. 当前场景最近原文、进入状态和 POV 约束。
3. 已确认的活跃人物状态、核心秘密、直接关系和关键物品/位置快照。
4. 活跃剧情线、伏笔、立即前因和预期后果。
5. 与进入/退出地点相关的移动规则和最短耗时约束。
6. H-RAG 召回的相关场景与原文。
7. 可选 KG 多跳路径、社区摘要和文风样例。

每个片段带 `source_id`、版本、叙事时间、模态、确认状态、适用 POV、相关性和可截断级别。

### 10.2 上下文冲突

已确认的结构化事实优先于派生摘要；更具体且适用于目标叙事时间的事实优先于宽泛摘要。两个已确认事实矛盾时不由检索分数裁决，而是标记冲突并请求作者选择或允许本次创作采用明确假设。

### 10.3 上下文断裂检测

生成前检查 ContextPack 是否缺少当前 POV、最近场景、立即动作和活跃剧情线。每完成一个 Beat，再比较生成内容与 `SceneEntryContract`、最近正文和计划退出状态，发现主题跳转、突然换地点、未交代人物出现或指代不明。

检查报告必须引用“前文状态”和“新文本范围”，不能只输出“上下文不连贯”。

## 十一、影响图与精确失效

### 11.1 Impact Graph

影响图节点包括 `SourceSpan`、已确认 Claim、人物/关系事件、PlotEvent、SceneRevision、ChapterOutput、摘要和索引切片。依赖边表达：

- `DERIVED_FROM`：结构化主张或摘要来自某段正文。
- `READS`：一次生成实际读取了某个版本。
- `CONTINUES`：场景承接上一场景状态。
- `AFFECTS`：事件改变人物、关系、物品或剧情线。
- `SUMMARIZES`：摘要覆盖哪些节点。
- `FORESHADOWS/PAYS_OFF`：伏笔联系。

### 11.2 影响传播

上游修改先计算变化范围、实体键、时间区间和语义类型，只沿匹配依赖边传播：

1. 直接来源被删除或修改的主张标记待复核。
2. 读取这些主张的场景进入 `LOCALLY_STALE`。
3. 只有场景退出状态发生实质变化时，才继续传播到后继场景。
4. 只重建覆盖受影响节点的摘要、Embedding 和社区。
5. 每个告警展示依赖路径、变化前后和建议动作。

拼写、标点和不改变语义的润色只更新正文版本与索引，不触发剧情级传播。抽取器无法判断时只生成低优先级建议，避免级联失效爆炸。

## 十二、生成质量控制

### 12.1 防止 AI 水字数

每个 Beat 在生成前声明至少一种有效推进：新行动、新信息、新决策、关系变化、情绪转折、冲突升级或伏笔变化，并声明停止条件。目标字数是软范围，不允许为了达到字数重复表达。

质量检查包括：

- 语义重复和同义改写循环。
- 对刚发生内容的无必要复述。
- 对话没有改变信息、关系或行动。
- 连续段落只有泛化感受、环境描写或套话。
- Beat 已达到停止条件后仍继续扩写。
- 场景目标长期没有阻力、选择或结果。

系统输出“可删除范围、重复对象和未推进的 Beat”，优先建议压缩，不自动改写作者已确认正文。不同类型小说可调整描写密度，不能把慢节奏一律判为水字数。

### 12.2 节奏与篇幅

场景按目标、阻力、转折和结果评估，而不是只计算字数。系统跟踪连续场景的动作/对话/描写比例、剧情线推进间隔、伏笔悬置时长和高潮密度，但这些均为创作建议。

### 12.3 文风和人物声音

文风样例只从作者确认正文中选择。每个主要人物维护可演进的 `VoiceFingerprint`：

- 句子长度和长短句分布。
- 口语/书面语比例、文白比例和敬语等级。
- 常用句式、停顿方式、称呼、语气词和疑问/反问偏好。
- 叙事视角下的感知词和禁用表达。

指纹是统计参考，不是僵硬模板；人物成长可以产生新的指纹版本。生成前将目标人物指纹和场景 POV 约束放入 ContextPack，生成后以对照片段做漂移报告。

### 12.4 套话与反套话过滤

项目维护两类可版本化词表：

- `ClicheBlacklist`：平台或作者明确不希望出现的套话、空洞开场、泛化转折和模型口癖。
- `VoiceLexicon`：特定人物允许或偏好的称呼、语气词和惯用表达。

过滤分为前置和后置：

1. **前置**：将黑名单、近期已用高频短语和人物禁用表达编译成生成约束，并要求 Beat 产生具体行动或信息。
2. **后置**：T1 规则/小模型扫描精确命中、模糊变体、重复句式和跨场景口癖；T2/T3 只复核高风险或语义变体。
3. **处理**：对未采纳草稿可建议替换或压缩；作者已确认正文只生成报告，不自动重写。

过滤器必须按项目和体裁配置，不能把文学性重复、角色刻意口癖或诗性排比一律判为套话。

### 12.5 幻觉和新设定

草稿中无法连接现有正典的新人物、地点、能力和历史事件标记为“可能新增设定”，而不是直接报错。作者可以确认新增、链接已有实体、限定为模态内容或删除。

## 十三、检查、报告与提交

### 13.1 三阶段检查

- **生成前**：上下文完整性、失效依赖、POV 和模态过滤。
- **生成中**：Beat 停止条件、重复、明显实体冲突和流式恢复。
- **生成后**：逆向抽取、时间线、人物/关系/剧情、衔接、水字数和风格报告。

### 13.2 报告去噪

报告按确认程度、影响范围和严重度排序；同一根因合并为一个问题；已忽略问题保存作用范围和期限。默认只显示当前选区/场景的高价值问题，作者可以展开全章或全书分析。

### 13.3 提交边界

一次局部提交原子保存：新 `SceneRevision`、接受的文本补丁、作者确认的结构化变化、来源、依赖边和工作区状态。未确认抽取可以继续挂起，不阻止正文提交。

章节发布提交保存：场景顺序、发布版 `ChapterRevision`、正式 `ChapterOutput` 和章节级剧情摘要。后台索引、KG 投影和社区摘要不进入提交事务。

### 13.4 并发和陈旧草稿

即使是单作者，也可能同时打开多个窗口或运行后台生成。每个补丁带基础版本；基础范围改变时进行局部三方比较。无重叠补丁可以合并，重叠部分交给作者选择，不能静默覆盖。

## 十五、核心不变量

1. 作者正文不会因抽取失败、模型低置信判断或索引故障而丢失或无法保存。
2. AI 输出、逆向抽取和社区摘要不会自动成为正典。
3. 场景和章节历史版本不可覆盖，局部补丁必须绑定基础版本和文本范围。
4. 正典主张必须有来源、模态、叙事时间或明确的未知值，以及作者确认状态。
5. 非 `ACTUAL` 模态不能作为物理世界硬冲突依据。
6. LLM 抽取结果不能直接触发确定性阻断。
7. 知情追踪只覆盖显式核心信息差；`UNTRACKED` 不等于“不知道”。
8. 上游变化只沿实际依赖传播，不能默认把全部下游章节标记失效。
9. KG、向量、H-RAG 摘要和 GraphRAG 社区均可从正典重建。
10. 普通续写不依赖 GraphRAG 可用；全局分析失败不阻止本地写作。
11. 所有检索片段都带项目、来源和版本，旧索引不能伪装为最新正典。
12. 人物成长可以更新阶段基准，偏离报告必须提供对照证据。
13. 作者可以用显式决议改变旧正典、接受有意跳切或忽略建议。
14. 工作区自动保存与正典提交分离，崩溃恢复不会产生半提交状态。
15. 派生任务失败只能降低检索和分析能力，不能破坏已确认正文。
16. 每件唯一关键物品在同一叙事时刻最多有一个有效持有人，所有转移和复制都有事件来源。
17. 影子实体在掉马前不会泄漏真实身份；掉马后通过关联事件合并视图，不覆盖历史来源。
18. 非超自然移动必须满足地点距离、路线和最短耗时；特殊移动必须引用已确认规则。
19. 伏笔检索优先使用目标窗口、触发条件和显式锚点，不依赖全书 Prompt 或单一向量相似度。
20. 存量导入先持久化原文，再异步结构化；任何批次失败都可从检查点恢复。
21. 语气指纹和套话黑名单可版本化，过滤器不能自动修改作者已确认正文。
22. 模型路由失败或降级必须保留任务不确定性和调用记录，不得伪装成高等级模型结果。
23. `fsck` 能发现正文文件、SQLite、工作区和派生索引之间的版本/哈希不一致，并优先恢复或请求选择。

## 十六、分阶段建设

### 16.1 第一阶段：可靠的本地写作闭环

- SQLite 正典存储、Scene/Chapter 版本和持久化工作区。
- 手写、局部 AI 辅写、TextPatch 和局部采纳。
- 逆向抽取候选、模态、置信仲裁和作者确认。
- SceneEntry/Exit、ChapterOutput 和基础衔接检查。
- ItemEntity/ItemEvent、LocationEntity 和基础空间耗时校验。
- FTS、相邻场景检索、基础 H-RAG 和可恢复任务。
- T0/T1 模型路由、套话黑名单、基础 VoiceFingerprint 和 `fsck`。
- 重复、水字数、POV、已确认硬事实的基础检查。

### 16.2 第二阶段：长篇连续性

- 人物阶段、关系事件、核心秘密和稀疏知情追踪。
- ShadowEntity、IdentityRevealEvent 和掉马影响追踪。
- 剧情线、伏笔、时间线和细粒度 Impact Graph。
- 伏笔目标窗口/触发调度、向量召回、KG 限深路径查询和摘要增量失效。
- 人物声音、节奏和上下文断裂评估。
- 全书导入、批量逆向抽取、导出和跨介质备份恢复。

### 16.3 第三阶段：可选全局智能

- 按卷、阵营和剧情线生成社区摘要。
- 有预算的离线社区检测和 GraphRAG 全局分析。
- 基于作者决议降低重复误报。
- 大项目索引性能、模型成本预算和本地/远程模型路由。

只有前一阶段的正确性和可恢复性验收通过，才启用下一阶段。GraphRAG 的存在不是第一版完成个人小说创作闭环的前置条件。
